## 1. 개요
- **한 줄 소개**: 보석 색마다 원소 속성이 있는 매치-3 퍼즐. 색을 모아 스킬 게이지를 채우고, 원소 스킬로 판을 뒤집는 60초 타임어택.
- **타깃 플레이 시간**: 1회 약 60초 (매치/연쇄 시간 보너스로 실제 70~90초). 상한 90초.
- **핵심 재미**
  1. 어떤 색을 먼저 모아 어떤 스킬을 쓸지 고르는 전략성 (게이지 6개)
  2. 연쇄(x1~x5) + 스킬 + 배율 스킬의 콤보 폭발
  3. Bejeweled Blitz Lightning식 긴장감 (줄어드는 타이머 바, 칭찬 팝업, 힌트)

## 2. 게임 규칙
| 항목 | 값 |
|---|---|
| 보드 | 8×8 (고정) |
| 보석 종류 | 6종 (불·물·풀·번개·어둠·빛), 색+모양 이중 구분 |
| 스왑 | **상하좌우 인접 2칸**만 교환. 대각선 불가 |
| 유효한 스왑 | 스왑 결과 가로 또는 세로로 **같은 종류 3개 이상** 연속이 생기는 경우만 확정 |
| 무효 스왑 | 150ms 교환 후 되돌림 + 흔들림 연출, 시간·점수 변화 없음 |
| 매치 판정 | 가로/세로 3개 이상 연속. 겹치는 줄(L/T/십자)은 하나의 그룹(연결된 같은 색 매치 칸의 합집합)으로 처리해 중복 계산하지 않음 |
| 중력 | 제거된 칸 위의 보석이 아래로 낙하 |
| 리필 | 빈 칸은 보드 위쪽에서 새 보석이 무작위(균등)로 낙하 |
| 연쇄 | 낙하/리필 후 새 매치가 생기면 자동 제거. 더 이상 없을 때까지 반복. 한 번의 플레이어 행동(스왑 또는 스킬)에서 이어진 연쇄 단계 수 = `cascadeStep` |
| 초기 보드 | 생성 시 매치 0개 + 유효한 수 ≥ 1 보장 (생성 후 검사, 실패 시 재생성) |
| 리필 시 보정 | 리필로 새로 생기는 보석은 일반 무작위. 연쇄는 허용(보너스) |
| 유효한 수 없음 | 연쇄 종료 시점에 유효한 수가 0이면 "NO MOVES" 팝업 + 보드 전체 재섞기(매치 0개·유효한 수 ≥1 보장될 때까지 재시도). 시간 페널티 없음 |
| 입력 잠금 | 제거/낙하/연쇄 애니메이션 진행 중에는 스왑 입력 무시(스킬 버튼도 비활성). 타이머는 계속 흐름 |
| 종료 | 시간 0초 → 진행 중인 연쇄까지 모두 정산한 뒤 결과 화면 ("TIME UP!") |

## 3. 원소 스킬 시스템

### 3.1 게이지 충전
- 색별 독립 게이지 6개. **일반 매치로 제거된 보석만** 충전. 스킬로 제거된 보석은 충전 0 (스킬 연쇄 루프 방지). 단 스킬 이후 자동 연쇄 매치는 일반 매치이므로 충전됨.
- 충전량 공식 (그룹 단위): `gain = size + (size - 3)` → 3매치 +3, 4매치 +5, 5매치 +7, 6매치 +9 (※ 기존 공식 `size + 2*(size-3)`은 예시와 불일치해 예시 기준으로 정정, Build 구현과 일치) (L/T도 size로 계산).
- 최대치(초안): 불 18 / 물 22 / 풀 18 / 번개 20 / 어둠 22 / 빛 24. 초과분은 버림(가득 차면 대기).
- 예상 밸런스: 60초 동안 색당 약 30~35 충전 → 한 판에 스킬 총 8~10회.
- 게이지가 가득 차면 해당 버튼이 반짝(펄스) + 효과음. 스킬 사용 시 해당 게이지는 0으로 초기화.

### 3.2 발동 방식
- **PC/모바일 동일**: 가득 찬 게이지 버튼을 클릭/탭 → 발동.
- **즉시형**(물·번개·어둠·빛): 버튼 탭 즉시 발동.
- **타깃형**(불·풀): 버튼 탭 → **조준 모드**(보드 테두리 강조 + "대상 칸을 선택하세요" 안내, 같은 버튼 재탭/ESC/바깥 탭은 취소, 게이지 소모 없음) → 보드 칸 탭 시 발동. 조준 중에도 타이머는 흐름. 조준 중엔 스왑 입력 비활성.
- 한 번에 하나의 스킬만 처리. 연출/연쇄 중에는 버튼 비활성(회색, 가득 찬 상태는 유지).

### 3.3 스킬 목록 (연출 포함)
| 색 | 원소 | 스킬 | 동작(초안 값) | 연출 |
|---|---|---|---|---|
| 빨강 | 불 | **화염 폭발** (타깃) | 선택 칸 중심 3×3(최대 9칸) 제거 | 중심에서 주황 원형 파동 + 칸 확대 후 소멸, 화면 살짝 흔들림 |
| 파랑 | 물 | **시간 정지** | 타이머 5초 정지. 활성 중 재발동 시 남은 정지시간을 5초로 갱신(누적 아님). 정지 중에도 매치 시간 보너스는 적립 | 타이머 바가 얼음색 + 서리 오버레이, 남은 정지 초 표시 |
| 초록 | 풀 | **덩굴 십자** (타깃) | 선택 칸의 행 + 열 제거(최대 15칸) | 선택 칸에서 4방향으로 덩굴 선이 순차로 뻗음 |
| 노랑 | 번개 | **연쇄 번개** | 현재 보드에 존재하는 색 중 무작위 1색을 골라 그 색 보석 최대 8개를 무작위로 제거 | 선택 색 보석에 번개 선이 60ms 간격으로 하나씩 이어지며 제거 |
| 보라 | 어둠 | **암흑 배율** | 8초간 모든 점수 ×2 (연쇄 배율과 곱연산). 재발동 시 8초로 갱신 | 점수판 보라 글로우 + 남은 초 표시 |
| 흰색 | 빛 | **빛의 인도** | 시간 +4초(상한 90초) + 가능한 수 1개를 8초간 힌트로 표시 | 흰 섬광 + 타이머 바 반짝 |

### 3.4 스킬 점수와 연쇄 처리
- 스킬로 제거된 보석: **칸당 10점** × 현재 배율(연쇄 단계 1 → x1, 어둠 활성 시 ×2). 시간 보너스는 없음.
- 스킬 제거 직후 중력/리필 → 이후 자동으로 생긴 매치는 **연쇄 단계 2, 3, …** 으로 진행(x2, x3 …). 스킬이 연쇄를 일으키면 보상이 커지는 설계.
- 스킬 사용 자체는 `cascadeStep`을 1로 시작하는 새 행동 단위로 처리(이전 행동의 연쇄와 이어지지 않음).

### 3.5 밸런스 의도
- 물·어둠·빛: 최대치를 높게 잡아 가끔 쓰는 "투자형". 불·풀: 낮은 최대치의 "자주 쓰는 처리형". 번개: 중간.
- 어떤 색도 단독으로 압도적이지 않도록, 점수 기대값은 불≈풀 < 번개 < 어둠(연쇄와 조합 시) 정도를 목표로 하고, 시간 확보는 물/빛이 맡는다.
- 수치는 `CONFIG`에 모아 Review 단계에서 조정 가능하게 한다.

## 4. 점수·시간·배율
**매치 점수 (그룹당, 기본)**: 3개 50 / 4개 100 / 5개 200 / 6개 이상 `200 + 100×(size−5)`.
**최종 점수** = 기본 점수 × `연쇄 배율` × `어둠 배율`.

| 연쇄 단계 | 1 | 2 | 3 | 4 | 5+ |
|---|---|---|---|---|---|
| 연쇄 배율 | x1 | x2 | x3 | x4 | x5 (상한) |

**시간 보너스 (그룹당, 일반 매치만)**: 3개 +0.25초 / 4개 +0.5초 / 5개 이상 +1.0초. 연쇄 추가 보너스 없음. (※ Review 결과 기존 값 0.5/1.0/1.5/+0.5는 한 판이 2분 이상 이어져 하향 조정) 남은 시간 상한 **90초**.

**칭찬 팝업** (한 번의 행동에서 판정, 가장 높은 등급 하나만 표시):
| 등급 | 조건 |
|---|---|
| GOOD! | 연쇄 단계 2 도달 또는 4매치 |
| GREAT! | 연쇄 단계 3 도달 또는 5매치 이상 |
| AWESOME! | 연쇄 단계 4 도달 |
| EXCELLENT! | 연쇄 단계 5 이상 또는 한 행동 총 득점 5,000점 이상 |
- 스킬 발동 시에는 스킬 이름 팝업("화염 폭발!" 등)을 별도로 표시.
- 팝업은 보드 중앙 위, 0.8초 스케일 인/페이드 아웃. 동시 1개(새 팝업이 이전 것을 대체).

**HUD 표시**: 점수(숫자 롤링), 현재 배율 `x1~x5`(연쇄 중 갱신, 종료 후 1초 뒤 x1로 복귀), 어둠 활성 시 `×2` 배지, 연쇄 카운터("CHAIN 3").

## 5. 특수 보석 (선택)
- **1차 릴리스: 제외.** 4매치/5매치는 점수·시간·게이지 보너스만 받는다 (위 표 적용).
- **2차 확장(후보)**: 4매치 → 폭발 보석(자신의 색 3×3 폭발), 5매치 → 하이퍼 보석(스왑한 색 전체 제거). 구현 시 `gem.special` 필드 추가만으로 확장 가능하도록 보드 모델에 `special: null` 슬롯을 남겨 둔다(구현은 안 함).

## 6. UI/레이아웃
**세로 모바일 우선**, 단일 컬럼(최대 폭 520px, 데스크톱은 가운데 정렬 + 배경 장식).

위→아래 구성:
1. **타이머 바**: 가로 전체. 남은 비율 표시 + 숫자(초). 10초 이하 빨간 점멸. 정지 중 얼음색.
2. **점수 영역**: 좌 점수, 중앙 CHAIN 카운터, 우 배율 `x3` (어둠 `×2` 배지 병기).
3. **보드**: 8×8 정사각형. 한 변 = `min(100vw − 24px, 100dvh − (상·하단 UI 높이), 520px)`. 칸 크기는 CSS 변수 `--cell`로 계산.
4. **원소 게이지 6개**: 가로 6등분, 각 버튼 ≥ 44×44px(터치 타깃). 보석 아이콘 + 세로/가로 채움 막대 + 가득 찼을 때 펄스. 접근성 위해 `aria-label`("불 게이지 12/18").
5. **하단 버튼**: 힌트 / 메뉴(일시정지) / 리셋.
   - 힌트: 가능한 수 1개를 3초간 깜빡임 표시. 쿨다운 8초(버튼에 쿨다운 표시). 점수 페널티 없음.
   - 메뉴: 일시정지 + 오버레이(계속하기 / 다시 시작 / 소리 on·off / 나가기→시작 화면).
   - 리셋: "다시 시작할까요?" 확인 후 새 게임.

**화면 구성**
- **시작 화면**: 제목, 최고 점수, [시작] 버튼, 간단 규칙 3줄(스왑, 게이지, 스킬), 소리 토글. 최초 1회만 짧은 튜토리얼 문구 표시(`tutorialSeen`).
- **카운트다운**: 시작 직후 3-2-1 (약 2초, 타이머는 GO 이후 시작).
- **종료 화면**: 최종 점수, 최고 점수(갱신 시 "NEW BEST!"), 통계(최대 연쇄, 스킬 사용 횟수, 총 매치 수), [다시 하기] [시작 화면].
- **반응형 기준**: 폭 ≤ 480px 세로가 1순위. 가로 모드·낮은 높이(`max-height: 500px` + landscape)에서는 게이지를 보드 오른쪽 세로열로 재배치. iframe(블로그 카드 임베드)에서도 부모 크기에 맞게 동작(뷰포트 단위 기반, 고정 px 최소화).
- `prefers-reduced-motion`이면 흔들림·파티클을 축소.

## 7. 입력 처리 (Pointer Events 사용)
- 보드에 `touch-action: none`, `user-select: none`. 이벤트는 보드 컨테이너에 **위임**(칸마다 리스너 X), 좌표→칸 변환은 `getBoundingClientRect` 기준.
- **클릭-클릭(탭-탭)**: 첫 탭 = 선택(강조), 인접 칸 탭 = 스왑 시도, 인접하지 않은 다른 칸 탭 = 선택 변경, 같은 칸 재탭 = 선택 해제.
- **드래그/스와이프 스왑**: `pointerdown` 칸 기록 → `pointermove`에서 이동 거리 > 칸 크기의 35%이면 우세 축 방향의 인접 칸과 스왑(한 번만 발동, 이후 입력 무시), `pointerup/cancel`에서 상태 초기화. `setPointerCapture` 사용.
- 드래그 미달 후 `pointerup` = 탭으로 간주(클릭-클릭 흐름과 통합).
- 조준 모드(불·풀)에서는 칸 탭 = 대상 확정. 스왑 로직 우회.
- 입력 잠금 중 입력은 무시(큐잉하지 않음). 일시정지/시작 화면/종료 화면에서는 보드 입력 비활성.
- (선택, 권장) 키보드: 방향키로 커서 이동, Space/Enter 선택·스왑, 1~6 키로 스킬 버튼, P 일시정지. 기본 플레이에는 불필요하나 접근성을 위해 최소 구현.

## 8. 렌더링/기술 방식
**선택: DOM + CSS (+ 인라인 SVG 보석 심볼)**

근거:
- 판이 8×8=64칸으로 작아 DOM 노드 수가 문제되지 않음.
- 이동/낙하/제거는 `transform` + CSS transition/animation으로 GPU 합성되어 충분히 부드럽고, 코드가 가장 단순.
- 반응형(칸 크기 `--cell`, 모바일 레이아웃)과 접근성(`aria-label`, 포커스, 큰 터치 타깃)이 CSS/DOM에서 자연스러움. 외부 라이브러리 불필요.
- Canvas는 파티클이 수백 개 이상일 때 유리하나, 본 게임은 DOM 요소 수십 개 수준의 파티클이면 충분. DPR/리사이즈 처리와 히트 테스트를 직접 구현해야 하는 부담이 더 큼.
- 파티클/번개 선 등 일부 연출은 CSS 애니메이션 + 임시 DOM(애니메이션 종료 후 제거)으로 처리. 한 시점에 파티클 DOM 최대 ~60개로 제한.

**보석 디자인 (색약 대응: 색 + 모양 + 내부 기호)**
| 종류 | 색(초안) | 외곽 모양 |
|---|---|---|
| 불 | 빨강 `#e5484d` | 삼각형(꼭짓점 위) |
| 물 | 파랑 `#3b82f6` | 원/물방울 |
| 풀 | 초록 `#30a46c` | 둥근 사각형 |
| 번개 | 노랑 `#f5c518` | 4각 별 |
| 어둠 | 보라 `#8e4ec6` | 육각형 |
| 빛 | 흰색 `#f4f4f5` (테두리 회색) | 마름모 |
- 색은 색약 안전을 고려해 명도 차이를 두고, 모양이 1차 구분 수단이다. 각 보석 안에 얇은 원소 기호(불꽃/물방울/잎/번개/달/해)를 SVG로 넣는다.
- 보석은 `<svg><use href="#gem-fire"/></svg>`처럼 하나의 SVG 스프라이트(`<symbol>`)를 공유.
- 설정에서 "고대비 모양 모드"(색 채도 낮춤 + 모양 윤곽 강조) 토글은 **범위 밖**.

**애니메이션 방식**
- 보드 상태(2D 배열)는 JS가 단일 진실 소스. DOM은 상태를 반영만 한다 (`render()`/`updateCell()`).
- 칸 위치는 `transform: translate(x, y)`로 배치, 이동은 `transition: transform`.
- 단계 진행은 `async/await` + `sleep(ms)` 기반(애니메이션 길이와 동일한 상수 사용). `transitionend`에 의존하지 않아 탭 전환·reduced-motion에서도 멈추지 않음.
- 기준 시간(초안): 스왑 150ms, 제거 220ms, 낙하 칸당 80ms(최대 400ms), 리필 낙하 동일.
- 타이머는 `requestAnimationFrame` + `performance.now()` 델타로 계산. `visibilitychange`로 탭 비활성 시 자동 일시정지.

**효과음 (WebAudio, 외부 음원 파일 없음)**
- 사용. `OscillatorNode` + 짧은 엔벨로프로 합성: 스왑, 무효 스왑, 매치(연쇄 단계에 따라 음 높이 상승), 게이지 충전 완료, 스킬 6종(각기 다른 파형/주파수 스윕), 칭찬, 종료.
- `AudioContext`는 **첫 사용자 입력(시작 버튼)에서 생성/resume** (모바일 정책 대응). 음량 낮게(마스터 gain 0.15 이하). 기본 ON, 메뉴/시작 화면에서 토글, `localStorage`에 저장. 오디오 초기화 실패 시 조용히 무음 처리.

## 10. 파일 구조
```
/apps/element-gems/
├─ spec.md      # 이 문서 (Plan)
├─ index.html   # 마크업(화면 4종: 시작/게임/일시정지/종료), SVG 스프라이트, 메타(viewport)

├─ game.js      # 단일 클래식 스크립트(IIFE). 내부를 섹션 주석으로 구분
```

- `file://`로 열어도 동작해야 하므로 ES Module(`type="module"`)은 쓰지 않는다. 파일이 커지면(>1,000줄) 클래식 스크립트 `board.js`(순수 로직) / `game.js`(UI·입력·연출)로만 분리한다.

- 외부 의존성 없음(CDN 미사용). 폰트는 시스템 폰트.

## 11. 구현 단계 분해 (Build 서브에이전트용)
각 단계 끝에 브라우저로 동작을 확인하고 다음으로 넘어간다.
1. **보드**: `index.html` 골격, 8×8 렌더링, 6종 SVG 보석(모양+색), 초기 보드 생성(매치 0, 유효한 수 ≥1), `--cell` 반응형 크기.
2. **스왑/매치**: Pointer Events 입력(클릭-클릭, 드래그), 인접 스왑, 매치 탐색(가로/세로, L/T 그룹화), 무효 스왑 되돌림.
3. **중력/연쇄**: 제거 → 낙하 → 리필 → 재검사 루프(`cascadeStep`), 입력 잠금, 유효한 수 없음 시 재섞기.
4. **점수/타이머**: 점수·배율·시간 보너스, rAF 타이머, 타이머 바, 칭찬 팝업, 시작/카운트다운/종료 흐름, 최고 점수 저장.
5. **원소 스킬**: 게이지 충전 로직·UI, 즉시형 4종 → 타깃형 2종(조준 모드), 정지/배율 상태 관리, 스킬 후 연쇄 처리.
6. **UI/연출**: 파티클·섬광·흔들림, 힌트 버튼(쿨다운), 일시정지/리셋 오버레이, 효과음(WebAudio), 키보드 접근성(선택).
7. **모바일 대응**: 세로/가로 레이아웃 점검, 터치 스와이프 정확도, 44px 터치 타깃, `touch-action`, 주소창 변화(`dvh`), iframe 임베드 크기 확인, `prefers-reduced-motion`.
- Build는 `/apps/element-gems/` 밖 파일(블로그 `index.html` 포함)을 수정하지 않는다.

## 15. 난이도 시스템 (초보 / 중수 / 고수) + 스킬 게이지 하향 (Plan 추가, 2026-11-07)
> 모든 수치는 **초안 값(시뮬레이션 보정)**. §16(2×2 정사각형 매치)이 **켜진 상태**를 기준으로 보정했다. 아래 표가 §3.1 최대치, §3.5, §4 시간 보너스, §6 힌트·시작 화면·`60초` 문구, §9 저장 구조, §13 Non-goals의 "난이도 설정"과 충돌하면 **§15가 우선(해당 항목을 대체)** 한다.

### 15.1 개요
- 사용자 요청: ① 세 가지 난이도 구성, ② 보석 스킬 게이지를 다 채우는 데 필요한 성공(매치) 횟수가 너무 많으니 전체적으로 낮추고 난이도로 한 번 더 조정.
- 이름: UI **초보 / 중수 / 고수**, 내부 키 `easy / normal / hard`. 기본 선택은 `normal`(중수). 조작·보드(8×8)·스킬 6종·연쇄·컷인 규칙은 모두 동일하고, 아래 **수치 프리셋**만 다르다.
- 현재(기존) 게이지는 캐주얼 기준 스킬 1회당 매치 그룹 약 **10개**가 필요했다(시뮬레이션). 이를 **초보 약 5개 / 중수 약 6개 / 고수 약 7개**로 낮춘다. 한 판 스킬 횟수는 기존 약 5회 → 초보 14 / 중수 9 / 고수 6회.

### 15.2 난이도별 프리셋 표 (`CONFIG.difficulty[level]` 값)

**선택한 조정 축과 이유** (5개): ① 게이지 최대치(필수) ② 시작 시간·상한·시간 보너스 — 판 길이를 90~120 / 70~90 / 50~70초로 가르는 가장 큰 레버 ③ 힌트(자동 힌트·쿨다운) — 초보가 막히는 순간을 줄이고 고수는 스스로 찾게 함 ④ 스킬 효과 강도 — 초보에 유리한 시간 스킬·배율 스킬을 길게, 고수는 짧게 ⑤ 점수 배율 + 난이도별 최고 점수 분리 — 난이도 간 점수 비교 방지.
- **보석 종류 수 결정: 3난이도 모두 6종 유지.** 스킬 6종 전부를 경험시키는 것이 이 게임의 핵심이다. 5종(초보) 대안도 시뮬레이션했다: 5종이면 매치 그룹이 +44%(한 판 약 70→102) 늘어 스킬 22회·판 길이 약 128초로 목표(12~16회/90~120초)를 크게 넘고, 한 원소 스킬이 사라진다(어둠을 빼면 배율 스킬 부재, 빛을 빼면 시간 보강 부재). → **기각**, 필요하면 열린 질문 1로만 남긴다.
- 고수의 최대치를 "현재 -15%"가 아니라 약 -33%로 한 이유: 고수는 시간이 짧아(50초) -15%(15/19/15/17/19/20)를 쓰면 캐주얼 기준 스킬이 한 판 약 4회로 목표(5~8회)에 못 미치고 스킬 1회당 약 9.7매치가 필요해 "너무 많다"는 원 불만이 고수에서 남는다(근거: 15.3의 보조 표). 난이도 차이는 최대치보다 **시간·힌트·스킬 강도·점수 배율**에서 낸다. 단조성(초보 < 중수 < 고수)은 유지.

**§ 대체 목록**: §3.1 최대치·"예상 밸런스 8~10회", §3.3 스킬 수치(표의 값은 중수 기준과 동일), §4 시간 보너스·상한(중수 기준 값만 변경: 0.25/0.5/1.0 → 0.2/0.4/0.8), §6 힌트 규칙, §1·§6 "60초" 문구(난이도별 값 표시), §13 Non-goals의 "설정 화면(난이도)".

### 15.3 시뮬레이션 (Node, `game.js` 순수 함수 + 근사)
**방법**: `game.js`의 `gaugeGain`, `timeBonusFor`, `baseScore`, `chainMult`, `applyGravity`를 그대로 사용하고(`require`로 불러 `CONFIG`를 프리셋으로 덮어씀), `findMatches`/`listMoves`/`hasValidMove`/보드 생성/재섞기는 §16 규칙(2×2)을 넣은 동일 로직의 복제본을 사용. 난이도당 **500판**(보조 모델 300판), 재현 가능한 시드. 게임 시계에 반영한 것: 수당 생각시간 + 스왑 150ms + 단계별 제거 220ms + 낙하(칸당 80ms, 최대 400ms, +30) + 스킬 연출 시간(컷인은 시계 정지이므로 제외) + 재섞기 0.95초. 스킬 효과는 근사(불·풀은 무작위 칸 조준, 번개는 무작위 색, 물은 정지, 어둠은 점수만, 빛은 시간만, 힌트 표시는 시계에 영향 없음).
**플레이어 모델**: ① **캐주얼**(기준): 무작위 유효 수, 수당 0.9~2.3초(평균 1.6초), 게이지 가득 시 60% 확률로 다음 수 대신 발동(발동 지연 약 1초). ② 느린 초보: 평균 2.4초, 발동 확률 50%. ③ 숙련: 12개 중 최대 제거 선택, 평균 1.0초, 즉시 발동.

### 15.5 저장 데이터 변경 (`element-gems:v1` 키 유지)
```json
{
  "level": "normal",
  "bestByLevel": { "easy": 0, "normal": 0, "hard": 0 },
  "bestChain": 0, "plays": 0, "lastScore": 0,
  "muted": false, "tutorialSeen": false, "cutin": true,
  "best": 0
}
```
| 필드 | 규칙 |
|---|---|
| `level` | `easy/normal/hard` 중 하나. 없거나 잘못된 값이면 `normal` |
| `bestByLevel` | 난이도별 최고 점수(배율 적용 후 점수). 종료 시 해당 난이도 값만 갱신 |
| `best` | **레거시**. 읽기 전용 이관용 + 롤백 대비로 `bestByLevel.normal`과 같은 값을 계속 미러링 기록 |
| `bestChain`, `plays`, `lastScore` | 난이도 공통(기존 그대로) |
- **마이그레이션(로드 시)**: `bestByLevel`이 없으면 `{ easy: 0, normal: best, hard: 0 }`로 만들고 `level = 'normal'`. 기존 `best`는 모두 중수 점수로 취급(기존 점수는 중수와 가장 가깝지만 시간·게이지가 달라졌으므로 "참고 기록"임). 이후 `bestByLevel`이 있으면 그 값을 신뢰. 모든 필드는 try/catch + 타입 검사로 기본값 대체(현재 `loadSave`는 값 타입이 같을 때만 복사하므로 **중첩 객체 `bestByLevel`은 전용 처리**가 필요).
- 키 접미사 `v2`로 분리하지 않는다(기존 데이터 호환 유지가 목적).

## 16. 2×2 정사각형 매치 규칙 (Plan 추가, 2026-11-07)
> 사용자 요청: "같은 보석 4개가 정사각형(2×2) 형태로 모였을 때도 클리어". §15의 난이도 수치는 이 규칙을 **켠** 상태로 보정했다. 기존 §2 매치 판정 행("가로/세로 3개 이상 연속")을 **확장·대체**하고, §2 초기 보드·유효한 수 행, §4 칭찬 "4매치" 조건을 이 절의 정의로 **대체**한다.

### 16.1 규칙 정의 (확정형)
1. **정사각형 매치**: 같은 종류 보석이 2×2 칸을 이루면 매치다. 기존 가로/세로 3연속 매치와 **함께** 판정하고, 둘 중 하나라도 성립하면 제거한다.
2. **그룹화**: 3연속과 2×2로 표시된 칸 중 **같은 종류이고 상하좌우로 이어진 칸의 합집합**이 한 그룹(기존 L/T/십자 규칙과 동일). 그룹 크기 = 합집합 칸 수. 단독 2×2 = 크기 4 그룹.
3. **보상**: 새 보너스 없음. 기존 그룹 크기 규칙 그대로(크기 4: 기본 점수 100, 게이지 +5, 시간 보너스는 4매치 값). 보상 상향이 필요하면 열린 질문.
4. **유효한 스왑**: 스왑 결과 3연속 **또는 2×2**가 생기면 유효(`trySwap`은 `findMatches(...).length`로 판정하므로 자동 반영). 무효 스왑은 기존대로 되돌림.
5. **초기 보드/재섞기/리필**: 초기 보드와 재섞기 결과는 **3연속·2×2 모두 0개 + 유효한 수 ≥1**. 리필로 생긴 정사각형은 연쇄로 허용.
6. **연쇄·칭찬**: 연쇄 단계·배율 규칙 그대로. 칭찬 "4매치(GOOD!)" 조건의 그룹 크기 ≥4에 2×2도 포함(`maxGroup`이 크기 기준이라 코드 변경 없음).
7. **스킬 제거와의 관계**: 변경 없음(스킬로 제거된 칸은 점수만, 게이지·시간 보너스 없음). 스킬 후 낙하·리필 뒤 자동 매치는 2×2 포함.
8. **시각 피드백(선택)**: 단독 2×2 제거 시 4칸 중심에 별 모양 반짝임 정도만 제안. 범위가 커지면 2차.

**경계 사례**
| 사례 | 결과 |
|---|---|
| 단독 2×2 (같은 색 4개) | 크기 4 그룹: 100점 ×배율, 게이지 +5, 시간 보너스(4매치 값) |
| 2×2에 같은 색 칸이 변으로 붙음 | 변으로 붙은 칸은 항상 2×2의 한 줄과 합쳐 가로/세로 3연속이 되므로 **자동으로 같은 그룹**(크기 5~). 대각선만 붙은 같은 색 칸은 제외 |
| 2×2 + 별개의 가로 3연속이 겹침(L/T 유사) | 합집합 1그룹(예: 2×2+3연속이 한 칸 공유 → 크기 6) |
| 3×3 같은 색 블록 | 전부 매치 → 크기 9 그룹 1개(기본 `200+100×4`=600점) |
| 2×3 같은 색 블록 | 크기 6 그룹 1개 |
| 서로 다른 색이 인접 | 색별로 별도 그룹(각각 점수·게이지·시간 보너스, 같은 `cascadeStep`) |
| 보드 가장자리·모서리 | 2×2는 `r∈[0,6], c∈[0,6]`의 모든 위치에서 성립(모서리 칸 포함). 경계 밖 접근 없음 |
| 연쇄 중 동시 발생 | 한 단계에서 3연속과 2×2가 동시에 있어도 한 번에 모두 제거, 단계 수는 1 증가 |
| 스왑으로 한 칸이 2×2와 3연속을 동시에 완성 | 합집합 1그룹으로 한 번 계산(중복 계산 없음) |

### 16.2 알고리즘 영향 범위
| 함수/위치 | 변경 |
|---|---|
| `findMatches(g)` | 3연속 마킹 뒤 **2×2 마킹 추가**(아래 의사코드). 그룹화(연결 요소)·반환 형태 `{type, cells, size}`는 변경 없음 → 점수·게이지·시간 보너스·칭찬 계산 코드 수정 불필요 |
| `lineAt` + 신규 `squareAt(g,r,c)` | `wouldMatch`가 스왑한 두 칸 각각에 대해 `lineAt \|\| squareAt` 검사. `squareAt`은 해당 칸을 포함하는 최대 4개의 2×2 검사 |
| `wouldMatch`/`listMoves`/`hasValidMove`/`findHint` | `wouldMatch`만 수정하면 나머지는 자동 반영(힌트가 2×2가 되는 수도 제안) |
| `generateBoard` | 칸을 채울 때 **3연속 회피처럼 2×2 완성도 회피**: `(r≥1,c≥1)`에서 `g[r-1][c-1]=g[r-1][c]=g[r][c-1]`이면 그 색을 후보에서 제외. 종료 시 `findMatches(g).length===0 && hasValidMove(g)` 검사 유지 |
| `shuffleTypes` | 기존 루프가 `findMatches`로 검사하므로 자동 반영(2×2 포함 0개 조건). 실패 시 `generateBoard` 폴백 |
| `trySwap` / `cascade` / `dropAndRefill` | 변경 없음(`findMatches` 결과 사용) |
| `awardGroup`/`charge`/`timeBonusFor`/`baseScore` | 변경 없음(그룹 크기 입력) |
| `module.exports` | `squareAt` 추가(테스트용) |

```
// findMatches 내부, 3연속 마킹 직후
for r in 0..R-2: for c in 0..C-2:
  t = g[r][c]
  if t != null and g[r][c+1]==t and g[r+1][c]==t and g[r+1][c+1]==t:
    mark[r][c]=mark[r][c+1]=mark[r+1][c]=mark[r+1][c+1]=true
// 이후 기존 연결 요소(같은 색, 마킹된 칸) 그룹화 그대로

wouldMatch(g,a,b): swap; ok = lineAt(a)||lineAt(b)||squareAt(a)||squareAt(b); swap back
squareAt(g,r,c): for dr,dc in {-1,0}x{-1,0}: top-left=(r+dr,c+dc) in bounds and 4칸 동일 종류면 true
```

### 16.3 밸런스 영향 (2×2 규칙 on/off 시뮬레이션, 캐주얼, 500판)
같은 프리셋(§15.2)·같은 시드 구성으로 규칙만 껐다 켠 결과.
| 프리셋 | 지표 | off | on | 변화 |
|---|---|---|---|---|
| 현재 값(참고) | 매치 그룹 수 / 스킬 / 판 길이(중앙값) | 50.1 / 4.5 / 80초 | 53.2 / 5.2 / 85초 | +6% / +16% / +5초 |
| 초보 | 〃 | 66.0 / 12.8 / 108초 | 69.6 / 14.1 / 112초 | +5% / +10% / +4초 |
| 중수 | 〃 | 50.7 / 8.6 / 83초 | 52.6 / 9.4 / 85초 | +4% / +9% / +2초 |
| 고수 | 〃 | 38.6 / 5.5 / 64초 | 39.8 / 6.0 / 65초 | +3% / +9% / +1초 |
- 해석: 2×2는 무작위 6색 보드에서 완성 확률이 낮아 매치 그룹이 약 3~6% 늘고 스킬이 약 9~16% 늘 뿐, 판 길이는 1~5초 늘어난다(스킬의 시간 보조 포함). 기존 생성기로 만든 무작위 보드의 **12.1%가 이미 2×2를 포함**하므로 생성 시 회피가 필요하다.
- **§15와의 정합**: §15 표는 위 "on" 열 기준이다. 규칙을 끈 경우에도 초보 12.8 / 중수 8.6 / 고수 5.5로 목표 범위 안이라 두 절이 서로 모순되지 않는다. 규칙 on 때문에 §15에서 별도 보정한 것은 없다(수치가 이미 on 기준).
- 한계: 캐주얼 모델은 정사각형을 노리지 않는다. 숙련 모델(최대 제거 선택)은 2×2를 우연히 선택하며 §15.3 보조 표에 포함됨. 실제 사람이 정사각형을 적극 노리면 효과가 다소 클 수 있음(Review 후속 관찰).

## 17. 플레이 시간 2분 + 스테이지(레벨 1~10) 시스템 (Plan 추가, 2026-11-07)
> 사용자 요청: ① "60초는 너무 짧다 → 기본 한 판을 **2분**으로", ② 난이도(초보/중수/고수)를 고른 뒤 **각 난이도에서 레벨 1~10 스테이지를 차례로 클리어**하는 구조로 변경, 스테이지별 목표 점수는 Plan이 판단해 설정. 모든 수치는 **초안 값(시뮬레이션 보정)**이며 근사 시뮬레이션 기준이다. 최종 확정은 실제 플레이 후 조정이 필요하다(§17.5 한계).
> **충돌 시 §17이 우선(대체)**: §15.2의 시작/상한 시간·시간 보너스·게이지 최대치, §15.4의 시작 화면 [시작] 버튼 역할·최고 점수 표시·`제한 시간 N초` 문구·종료 화면(NEW BEST), §15.5의 저장 구조(확장), §15.8 질문 2의 "경과 90초 이후 보너스 ×0.5"(→ 제거), §4·§6의 타이머 표기, §12·§15.7 체크리스트의 시간 값(65/60/50, 95/90/75). 그 외(점수 배율 ×0.8/×1.0/×1.3, 힌트, 스킬 효과 수치, 2×2 규칙, 컷인)는 그대로다. §1~§16 본문은 고치지 않았다.

### 17.3 스테이지 시스템 규칙
**흐름**: `시작 화면`(난이도 3버튼 + [시작]) → `레벨 선택 화면`(1~10) → 카운트다운(레벨·목표 표시) → 플레이 → 결과(클리어/실패) → (다음 레벨 / 다시 하기 / 레벨 선택).
```
[시작 화면] --시작--> [레벨 선택] --레벨 탭--> [카운트다운] --> [플레이] --> [결과]
     ^                  |  ^                                        | 클리어: 다음 레벨 / 다시 하기 / 레벨 선택
     └----- 뒤로 -------┘  └----------- 레벨 선택 ------------------┘ 실패: 다시 도전 / 레벨 선택
```
| 항목 | 규칙 |
|---|---|
| 클리어 | 행동(스왑·스킬) 종료 후 연쇄가 모두 정산된 시점(`runAction` 끝)에 `점수 ≥ 목표`이면 즉시 클리어 → "STAGE CLEAR!". 이 경우 "NO MOVES" 재섞기는 생략. 점수는 §15 난이도 배율 적용 **표시 점수** 기준 |
| 시간 종료 | 시간 0 → 진행 중인 연쇄 정산(§2) → 그 시점에 `점수 ≥ 목표`면 클리어, 아니면 실패("TIME UP", 같은 레벨 재도전). 정산 중 목표를 넘으면 클리어 |
| 클리어 후 | 남은 시간·연쇄는 버림. 별 판정은 클리어 순간의 `timeLeft / 시작 시간` |
| 잠금 | 난이도마다 `progress`(클리어한 최고 레벨, 0~10). 레벨 N 선택 가능 = `N ≤ progress + 1`. 이미 클리어한 레벨은 재도전 가능(별은 최고치만 갱신) |
| 난이도 변경 | 시작 화면에서만(기존 규칙). 레벨 선택 화면에서는 난이도 표시만 하고 변경하려면 뒤로 가기 |
| 레벨 10 클리어 | 결과 화면에 "{난이도} 완료! 축하해요" 문구, [다음 레벨] 버튼 없음 |
| 별(권장) | ★ 클리어 / ★★ 남은 시간 ≥ 시작 시간의 30% / ★★★ ≥ 50% (중수 기준 36초·60초 남음). 스킬로 시간을 늘려 남은 시간이 시작 시간을 넘어도 그대로 비율 계산 |
| 점수 외 난이도 요소 | **없음**. 목표 점수 곡선만으로 클리어율 98%→10%를 모두 커버한다(§17.4). 시간 보너스를 레벨별로 깎는 방안은 보너스 총량이 판당 약 3~8초(5% 이하)라 레버리지가 작아 기각 |
| 일시정지 | 계속하기 / 다시 시작(같은 레벨) / 소리 / 컷인 / 나가기(**→ 레벨 선택**). 오버레이에 "중수 · 레벨 3 · 목표 9,200" |

**별 등급 시뮬레이션(중수, 클리어한 판 중 비율)**
| 레벨 | 모델 | ★★(남은 ≥30%) | ★★★(≥50%) |
|---|---|---|---|
| 1 | 캐주얼 / 중급 / 숙련 | 70% / 99% / 100% | 24% / 70% / 99% |
| 5 | 캐주얼 / 중급 / 숙련 | 22% / 67% / 99% | 3% / 17% / 72% |

### 17.4 난이도 × 레벨 목표 점수와 예상 클리어율
**설계**: 중수 목표를 캐주얼 모델 점수 분포의 분위수로 배치(클리어율 100%→약 10%, 초반 완만·후반 가파름). 초보 = 중수 × 0.94, 고수 = 중수 × 1.06(100점 단위 반올림)으로 **같은 레벨 번호에서 목표 점수와 체감 난이도 모두 초보 < 중수 < 고수** 순서가 되게 함. 레벨 1은 슬로우 모델(수당 2.4초)도 60~87%가 통과하도록 낮게 시작.

### 17.5 시뮬레이션 방법·가정·기준선·한계
**방법**: `game.js`의 순수 함수(`findMatches`·`listMoves`·`hasValidMove`·`applyGravity`·`generateBoard`·`shuffleTypes`·`fireCells`·`grassCells`·`baseScore`·`chainMult`·`timeBonusFor`·`gaugeGain`·`applyDifficulty`)를 Node `require`로 불러 사용하고 `CONFIG.difficulty`만 덮어썼다. 시드 고정 난수. 스크립트는 세션 scratchpad에만 있고 저장소에는 없다(재현은 아래 가정대로 구현).
**게임 시계 모델**(실제 `advance`/`runAction`과 동일하게): 수당 생각시간(시계 흐름) + 스왑 150ms + 단계별 제거 220ms + 낙하(칸당 80ms, 최대 400ms, +30ms) + 재섞기 0.95초 + 불 160ms·풀 500ms·번개 `개수×60+140`ms + **컷인 1.3초는 시계 정지**(체감 시간에만 더함, 건너뛰기 없음 = 보수적). 물 정지 중에는 타이머 정지(체감 시간은 흐름), 어둠 ×2는 지속 시간 동안 점수(스킬 칸 포함), 빛은 시간만, 시간 보너스는 일반 매치 그룹마다 적립(상한 `time.max`), 시간 소진 시 진행 중 행동까지 정산. 점수는 `baseScore × chainMult × (어둠 ×2) × scoreMult`(스킬 칸 10점).
**플레이어 모델**: 슬로우 = 무작위 유효 수, 수당 1.4~3.4초(평균 2.4), 게이지 가득 시 50% 발동(지연 1.5초). **캐주얼(기준)** = 무작위 유효 수, 0.9~2.3초(평균 1.6), 60% 발동(지연 1.0초). 중급 = 4개 중 최대 제거 선택, 0.8~1.8초(평균 1.3), 80% 발동. 숙련 = 12개 중 최대 제거, 0.6~1.4초(평균 1.0), 즉시 발동. 빠른 숙련(0.4~0.8초)은 수렴 확인용. 불·풀은 조준을 무작위 칸으로 처리(실제 사람은 더 잘 맞춤 → 점수 과소), 자동 힌트·힌트 버튼은 시계에 영향 없다고 가정.

### 17.7 저장 구조(`element-gems:v1` 유지)와 마이그레이션
기존 `level`(= **난이도**)·`bestByLevel`·`best`는 의미 그대로 두고, 새 키만 추가한다. 새 키 이름은 `progress`/`stages`로 "난이도" 의미의 `level`과 구분.
```json
{
  "level": "normal",
  "progress": { "easy": 0, "normal": 0, "hard": 0 },
  "stages": {
    "easy":   [ { "best": 0, "stars": 0 }, ... 10개 ],
    "normal": [ ... 10개 ],
    "hard":   [ ... 10개 ]
  },
  "bestByLevel": { "easy": 0, "normal": 0, "hard": 0 },
  "best": 0, "bestChain": 0, "plays": 0, "lastScore": 0,
  "muted": false, "tutorialSeen": false, "cutin": true
}
```
| 필드 | 규칙 |
|---|---|
| `progress[diff]` | 해당 난이도에서 클리어한 최고 레벨 0~10. 레벨 N 선택 가능 = `N ≤ progress + 1` |
| `stages[diff][i]` | 레벨 i+1의 `best`(그 레벨에서 도달한 최고 점수, 실패 포함, ≥0)와 `stars`(0~3, 최고치만 갱신, 0 = 미클리어) |
| `bestByLevel`, `best` | **UI에서 더 이상 쓰지 않음**(60초 판 기록이라 2분 판과 비교 불가). 값은 보존만 하며 갱신하지 않는다. 롤백 대비로 지우지 않음 |
| 불일치 방지 | 로드 시 `progress`를 `max(progress, 별이 1 이상인 최고 레벨)`로 보정, 범위 밖/비정수/NaN은 기본값. `stages`는 배열 길이 10·원소 타입 검사(중첩 객체는 `bestByLevel`처럼 전용 처리), 실패 시 해당 난이도만 기본값 |
| 마이그레이션 | `progress`·`stages`가 없으면 전부 0/빈 값으로 생성. 옛 데이터(`best`, `bestByLevel`, `level` 등)는 그대로 열리되 진행도는 **레벨 1부터**. 키 접미사 `v2`로 분리하지 않음. 깨진 JSON/`localStorage` 차단 시 메모리 상태로 동작 |
| 쓰기 시점 | 스테이지 종료(클리어/실패) 시 1회, 난이도 선택 변경 시(기존) |

### 17.10 열린 질문 (승인 시 결정)
1. **즉시 클리어 vs 종료 시 판정**: 초안은 "목표 점수에 도달하면 즉시 클리어"(남은 시간은 별 등급에 반영)입니다. "2분을 끝까지 하고 점수로 판정"이 더 낫다면 별은 점수 배수(130%/160%)로 바꿀 수 있습니다(그 경우 판 길이가 항상 약 2분 45초가 되어 짧게 끝내고 싶은 어린이에게는 지루할 수 있음). 즉시 클리어로 확정할까요?
2. **별 등급**: 남은 시간 30%/50% 기준의 ★1~★3을 넣을까요(초등학생 동기부여), 아니면 클리어/미클리어만 둘까요?
3. **시작 시간**: 중수 120초로 하면 시간 소진 판의 체감은 약 2분 45초입니다(컷인·정지 때문). 실제로 2분 안팎이 되게 **시작 100초**(체감 약 2분 17초, 스킬 12회, 목표 점수 약 -18% 재산정 필요)로 낮출까요? 초안은 사용자가 말한 "2분 = 타이머 표기 2:00"을 우선했습니다.
4. **목표 곡선 상단**: 현재 레벨 10은 캐주얼 9%이지만 계획을 조금 세우는 중급 플레이는 중수 65%·고수 44%가 깹니다. 레벨 9~10을 더 올려(예: 중수 L10 18,000) 숙련자 전용으로 만들까요?
5. **기존 최고 점수**: 60초 판 기록(`best`/`bestByLevel`)은 UI에서 숨기고 보존만 합니다(초안). 완전히 삭제(0으로 초기화)할까요? 그리고 시간 보너스를 아예 없애 더 단순하게 만들까요(목표 점수 약 -4% 조정, 초안은 25% 유지)?
