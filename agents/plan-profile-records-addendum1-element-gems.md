# 추가 지침 1 — 범위 축소와 1단계 수정 (이전 지침의 일부를 **대체**)

원 지침: `agents/plan-profile-records-element-gems.md`. 이 문서는 사용자가 방금 바꾼 요구를 담으며, 아래 두 가지를 **대체**한다. 충돌하면 이 문서가 우선이다. 이미 쓴 내용은 필요한 만큼만 고친다(기존 § 번호 §23 안에서 고치는 것은 허용, §1~§22는 여전히 수정 금지).

## 대체되는 것
1. **2단계(다중 프로필 최대 3개) 전체는 철회됨**(사용자: "약간 무리가 있으니 1단계만"). 계획서에서 2단계 본문은 빼고, "철회됨·범위 밖 후보" 한 줄과 "1단계가 나중의 다중 프로필을 막지 않는지" 메모 한 줄만 남긴다. 이미 조사한 운영·서버 분석(별 0개 프로필은 순위 인덱스 제외, 등록 한도, 용량 환산 등)은 아래 1번 평가에 필요한 만큼 재사용한다.
2. 원 지침 1단계의 **"지우기 선택(프로필만 지우기=기록 유지 / 프로필과 기록 모두 지우기)"** 와 **"새 프로필 때 [가져오기]/[새로 시작]"** 은 폐기한다. 새 규칙은 아래다.

## 새 1단계 규칙 (사용자 결정, 2026-11-08)
사용자는 각자 기기를 쓰는 학교 환경이라고 했다. 목적: **다른 프로필이 이 기기에 남은 기록을 이어받는 일이 없게** 하고, **랭킹에는 지운 프로필이 남게** 하는 것.

### 규칙 1 — 프로필 지우기: 이 기기의 프로필과 게임 기록을 함께 삭제
- 삭제 대상(기록 범위를 표로 정의): 일반용 `element-gems:v1`, 교육용 `element-gems-edu:v1`(교육용은 학습 통계 `edu.stats`·문제 bag `edu.pool`·선택한 학습단원 `edu.unit` 포함), 프로필 `element-gems:profile:v1`, 동기화 상태(앱별 `element-gems:sync:v1`·`element-gems-edu:sync:v1`), 순위표 캐시 `element-gems:hall:v1`. 두 앱은 같은 origin이라 **한쪽 앱에서 다른 앱의 키도 지울 수 있다**. 소리·컷인 같은 **설정은 기록이 아니므로 유지**하는 것을 권장안으로 하고 근거를 쓴다(다른 키가 더 있으면 코드에서 찾아 빠짐없이).
- **선택지 두 개**(확인창, 어린이가 읽는 쉬운 말):
  - ① **이 기기에서만 지우기 — 순위표에는 남아요**: 서버 `POST /api/delete`를 **부르지 않는다**(서버 변경 없음). 사용자가 원한 동작이다.
  - ② **순위표에서도 지우기**: 서버 행 삭제(`POST /api/delete`) + 기기 삭제. **사용자가 요청하지 않았고 메인 세션이 안전을 위해 추가 제안한 선택지**이므로 계획서에서 "확정 대기(열린 질문 1, 권장: 추가)"로 표시한다. 사용자가 거절하면 ①만 남긴다.
- 확인창에 꼭 들어갈 경고(쉬운 말): ①을 하면 **이 프로필을 다시 불러오거나 나중에 지울 수 없어요**(번호표가 이 기기에만 있어서 서버가 누구 것인지 모름; 운영자만 지울 수 있음). 기록은 **되돌릴 수 없고** 서버에도 사본이 없다. 닉네임·그림만 바꾸려면 **'수정'** 을 누르라는 안내(수정은 기록 유지). 기록까지 지우므로 **한 번 더 확인**한다.
- 지우기 직전에 **아직 못 보낸 기록(오프라인 대기)** 이 있으면 ①에서 마지막 전송을 한 번 시도하고, 실패하면 "순위표에 마지막 기록이 반영되지 않을 수 있어요"를 알린다(코드로 동작 확인, 서버 오프라인에서도 지우기는 성공해야 한다 — 서버가 없거나 실패해도 게임은 완전히 동작).
- **①의 서버 쪽 결과를 평가해 계획서에 쓴다(확인함/추정 구분)**: 지운 프로필의 서버 행은 소유자(pid)가 기기에만 있으므로 **고아 행**이 된다. 서버에는 **자동 정리(Cron 등)가 없다**(메인 세션이 `grep`으로 확인함 → 고아 행은 영구히 남음, 운영자 SQL `DELETE`로만 지움). 별이 1개 이상이면 순위 인덱스에 계속 포함된다. 닉네임+번호표는 공개로 남는다(실수로 실명·부적절한 닉네임을 올렸을 때 사용자가 스스로 지울 수 없어서, 전체 이용가·어린이 대상 원칙과 spec §19.3.4의 "언제든 지울 수 있어요" 안내 문구와 어떻게 맞출지 — ②가 그 구제책). 한 사람이 지우고 새로 만들기를 반복하면 순위에 별 있는 행이 늘어난다(등록 한도 시간당 100/IP만 완화). spec §19.4.7 용량 계산에 비춰 영향을 숫자로 환산하고(가정 명시), 화면 문구(§19.3.4)·관리자 정리 절차(§19.4.6)·`CLAUDE.md` 서버 규칙(개인정보 최소화)에 필요한 변경 제안을 적는다(CLAUDE.md는 직접 고치지 않고 제안만).

### 규칙 2 — 새 프로필 만들기는 항상 처음부터
- 사용자 지시: "새 프로필을 만들면 무조건 기록 초기화(처음부터)". 새 프로필의 첫 `/api/sync`에는 **기록을 올리지 않는다**(빈 기록). 규칙 1로 지우면 기록이 삭제되므로 **다른 프로필이 이어받을 기록 자체가 없다**(서버 삭제 여부와 무관) — 이 보장을 계획서에 명시하고 Review 체크리스트에 넣는다.
- **예외 후보(열린 질문 2, 권장안 먼저)**: 프로필 없이 시작("나중에 할래요")해서 이 기기에 별 기록이 쌓인 학생이 나중에 **처음** 프로필을 만들 때 "무조건 초기화"면 그 기록이 사라진다. 권장: 프로필 이력이 없는 기기에서 첫 프로필을 만들 때는 그 기록을 **이어서 쓴다**(질문 없이 승계; 지운 뒤에는 기록이 이미 삭제돼 있어 승계할 것이 없으므로 사용자 의도 "다른 프로필이 이어받기 방지"는 유지). 대안: 사용자 지시 그대로 무조건 초기화(확인창 한 줄로 "기록이 사라져요" 경고). **계획서 본문은 사용자 지시(무조건 초기화)를 기본으로 쓰고 예외안을 대안으로 병기한다.** 사용자 답이 오면 메인 세션이 알려 준다.
- 프로필 **수정**(닉네임·그림 변경)은 기록을 건드리지 않는다.

## 그대로 유지
원 지침의 배경 사실·필독·작업 규칙·파일 소유권·완료 보고 형식, 일반용·교육용 동시 반영(`tools/SYNC.md`, `[EDU]` 표식), §22 Build가 같은 파일을 고치는 중이라 이 Build는 §22 완료 뒤로 잡는다는 점, 화면 시안(이제 **확인창 2종(이 기기에서만 / 순위표에서도)** 과 **새 프로필 만들기 화면**, 규칙 2 예외안의 확인 한 줄). 서버 변경 없음이 전제.
