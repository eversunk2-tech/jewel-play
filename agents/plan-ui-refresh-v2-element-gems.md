# Plan 지침 — 메뉴 화면 시안 재작업: **태블릿 가로 기준**, 시각적으로 뛰어난 웹사이트를 참고 (spec §32 신규)

## 역할
너는 **Plan 담당**(Sonnet 서브에이전트)이다. 구현하지 않는다. 결과는 `apps/element-gems/spec.md` **맨 끝에 `## 32.`로 한 번에 추가**한다(`cat >> spec.md <<'EOF' … EOF`, 기존 §는 **읽기만**, 수정·삭제 금지). 번호는 **§32로 예약**되어 있다(§29·§30·§31은 이미 있음 — 먼저 읽는다). 쓰기 직전에 `tail`로 파일 끝이 바뀌었는지 확인한다.
프로젝트 규칙은 `CLAUDE.md`, 진행 상황은 `docs/STATUS.md` §14를 먼저 읽는다.

## 사용자 피드백 (2026-11-08, 질문 도구 응답 — 원문)
1. §29의 시안 A·B·C·D를 본 뒤: "**현재보다 딱히 나아진 것 같지가 않아. 그리고 태블릿 가로 화면을 기준으로 생성해줘. 시각적으로 멋지게 디자인된 웹사이트를 참고해서 다시 시안을 만들어줘.**"
2. 글꼴 질문에: "**글꼴은 다운받아도 되는데, 일단 현재 화면이 더 좋다고 판단돼. 레벨 선택 화면만 B안으로 바꾸면 되겠어.**"
3. 결과 팝업(클리어·실패): **이번에는 제외.**

### 메인 세션의 해석 (이 해석으로 진행하고, §32 머리말에 그대로 기록한다)
- **레벨 선택 화면 = §29의 B안(정글 길 지도 + 보석 친구)으로 확정**(사용자 승인). 모든 시안에 이 화면을 넣되 **가로 태블릿 구도에 맞게 지도를 다시 설계**한다(가로 폭을 쓰는 구불구불한 길, 노드 10개, 현재 레벨 강조 — §29의 B 시안은 세로 폰 기준이었다).
- **§29의 A·C·D는 "현재보다 낫지 않다"는 평가로 철회**한다(§32 머리말에 "§29 A·C·D 철회됨, 이유: 사용자 평가 — 변화가 작아 현재보다 나아 보이지 않음"). B 중 레벨 선택 부분만 살아남는다. **같은 수준의 미세 조정(글꼴 교체·립 규칙·간격·구도 소폭 변경)을 다시 내지 않는다.**
- **나머지 메뉴 화면은 "한눈에 보아도 확실히 더 멋진" 새 시안 3가지**를 만든다(아래). 사용자는 현재 화면(스카이 캔디·정글 배경·로고·젤리 보석)을 마음에 들어 하므로 **그 정체성은 유지**하되, 첫 화면의 **구성·깊이·타이포 대비·움직임**이 눈에 띄게 달라야 한다.
- 글꼴: 사용자가 "다운받아도 된다"고 했다 → **OFL 등 재배포 가능한 글꼴을 공식 출처(Google Fonts 공식 저장소/배포 페이지, 글꼴 저작자 공식 저장소)에서 받아 시안용으로 쓸 수 있다.** 받은 파일은 scratchpad의 **새 빈 폴더**에만 두고(프로젝트에 넣지 않는다), 라이선스 전문을 읽어 요약하며, 파일명·출처 URL·크기를 §32에 적는다. 앱에 포함하는 것은 시안 승인 뒤 Build의 몫이다. 위 다운로드 말고는 파일을 받지 않는다.

## 범위
- **대상(IN)**: 루트 `index.html`의 교육용/일반용 **선택 화면**, **시작 화면/메인 메뉴**(일반용·교육용), **레벨 선택**(B 확정), **프로필 만들기/고치기**, **명예의 전당**, 교육용 **학습단원 선택**·**모드 선택**. (교육용 화면은 `apps/element-gems-edu/`.)
- **제외(OUT)**: 게임 화면(HUD·보드·보석·게이지), 컷인, 게임 중 문제 팝업, **결과 팝업**(이번엔 제외). 이들은 바꾸지 않고 **이웃 기준**으로만 쓴다. 각 안마다 **"메뉴 → 게임 시작" 전환 장면 한 쌍**을 찍어 이질감이 없는지 보인다(§29에서 쓴 `.menu-screen` 격리 방식과 `diffgame.js` 게임 화면 불변 시험을 **재사용**한다: 읽기 전용 참고 `…/scratchpad/plan-ui/`).

## 기준 화면: 태블릿 가로
- 주 캔버스 **1180×820**(iPad Air 가로)와 **1024×768**(iPad 가로), **1280×800**(PC 작은 창/갤럭시 탭). 학교 기기(태블릿·크롬북)가 주 사용 환경이다. **폰 세로(390×844)는 맞는지 확인하는 용도**로만 시작·레벨 선택 두 화면을 찍는다.
- 현재 앱의 와이드 레이아웃 규칙은 spec **§20**과 `style.css`의 와이드 구간을 읽고, 현재 메뉴가 태블릿 가로에서 어떻게 보이는지(빈 공간, 카드가 가운데 한 줄로 서는 문제 등) **현재 화면을 같은 크기로 다시 찍어** 감사한다.

## 해야 할 일
### 1. 참고 사이트 조사 — "시각적으로 멋지게 디자인된 웹사이트"
- WebSearch·브라우저(읽기 전용, 로그인·다운로드 금지)로 **시각적으로 뛰어나다고 평가받은 웹사이트 10~15곳**을 찾는다(예: Awwwards·CSS Design Awards·FWA 같은 수상·큐레이션 목록, 게임·엔터테인먼트·어린이 제품·교육 서비스의 인터랙티브 랜딩/타이틀 페이지, 일러스트 중심 사이트, 풀스크린 장면 구성 사이트). 모바일 게임 UI가 아니라 **웹사이트의 첫 화면 연출**을 본다.
- 각 사이트마다: URL, 무엇이 뛰어난가(구도·깊이 레이어·타이포 스케일 대비·색 블로킹·일러스트 통합·모션 안무·여백·스크롤/진입 연출), **이 게임 메뉴에 옮길 수 있는 원리**, 옮길 때의 비용(정적 파일·CSS·SVG만 가능한가, WebGL 필요한가, 저사양 학교 태블릿 성능). **원리만 가져오고 그대로 따라 하지 않는다**(저작권·연상 금지 규칙, CLAUDE.md). 원문을 길게 옮기지 말고 요약+URL. 스크린샷은 분석용으로만 보고 **사용자에게 보내는 시안 보드에는 넣지 않는다**. 접근이 막히면(403 등) 막혔다고 쓰고 다른 곳을 찾는다. 못 찾은 것은 못 찾았다고 쓴다.
- 결과를 **"이 게임 메뉴에 적용할 시각 원리" 표**(원리 → 메뉴에서의 모습 → 비용)로 정리한다.

### 2. 새 시안 3가지 (서로 **크게** 다른 방향)
- 방향 후보(시작점일 뿐, 더 나은 것을 제안해도 된다): ① **풍경 속 타이틀**(여러 겹의 정글·하늘 레이어로 깊이감, 로고와 보석 친구 히어로, 메뉴가 풍경 안의 오브젝트처럼 놓임) ② **좌우 분할 쇼케이스**(왼쪽 대형 히어로 영역 + 오른쪽 메뉴 패널, 가로 태블릿의 폭을 의도적으로 사용) ③ **스크랩북/탐험 수첩**(종이·지도·스티커 질감의 큰 장면, 손으로 붙인 듯한 구성). 각 방향의 **타이포 대비**(아주 큰 제목 대 작은 보조), **색 블로킹**, **모션 안무**(진입·대기·눌림)까지 구체적으로 정한다.
- 안마다: 이름·컨셉 한 줄, 참고 원리(위 표와 연결), 화면별 변경(선택 화면, 시작, **레벨 선택(B를 가로로)**, 프로필, 명예의 전당, 교육용 단원·모드 선택), 디자인 토큰(색 HEX·대비 4.5:1 측정, 글꼴, 반경·외곽선·그림자·질감), **에셋**(기존 `assets/`의 배경·보석·아바타·로고를 우선 재사용; 새 일러스트가 필요하면 종류·크기·장수·WebP 용량·생성 방법과 프롬프트 초안 — 생성은 사용자 로그인이 필요하므로 **하지 않는다**, 사람 캐릭터 규칙·유명 작품 연상 금지), **용량**(첫 방문~첫 판 시작까지 직전 대비 +10% 이내, 지연 로드, 저장소 증가분 숫자, 5MB 초과면 사용자 확인), 성능(저사양 태블릿: `blur`·큰 필터·무한 애니메이션 남용 금지), 접근성(WCAG AA, `prefers-reduced-motion` 시 정지, 터치 타깃 44px, 모양으로도 구분), 두 앱 동기화(`style.css`·`ranking-ui.js`·프로필 화면 구간은 두 앱 소스 동일 — 시험이 검사함, 교육용 `edu.css`·`edu.js`).
- **시안은 실제 렌더링**: 현재 DOM·CSS 사본에 덮어쓰기 CSS/SVG/이미지만 얹어(§29 방식) 1180×820·1024×768·1280×800에서 찍는다. 파일: `…/scratchpad/plan-ui2/shots/` 아래 `{안}-{화면}_{기기}.jpg`(안 0 = 현재, 새 안은 V1·V2·V3). **같은 상태·같은 크기의 "현재 | V1 | V2 | V3" 나란히 보드**를 화면마다 만든다(1180×820 기준 필수, 1024×768은 시작·레벨 선택만, 폰 세로는 시작·레벨 선택만). 메뉴→게임 전환 쌍은 안마다 1180×820.
- **자기 비판 필수**: 각 안을 현재 화면과 같은 크기로 나란히 놓고 "한눈에 확실히 더 낫다고 말할 수 있는가"를 판정해 §32에 쓴다. 사용자는 §29의 변화가 작아 "나아진 것 같지 않다"고 했으므로, **변화가 작은 안은 스스로 버리고 더 과감하게 다시 만든다**(최대 2번 다시 시도). 끝까지 약한 안이 있으면 솔직하게 "약함"이라 쓴다. 현재 화면을 해치는 안(밝은 스카이 캔디 분위기·로고·젤리 보석 훼손)은 제외한다.

### 3. 권장·단계·충돌
- 비교표(현재보다 나아 보임·비용·에셋·성능·충돌 위험·정체성 보존)로 **한 안을 권한다**(조합 가능, 어떤 요소를 합치는지). "AI 느낌 점검표"(§29.10)를 가로 태블릿 기준으로 갱신해 Review가 예/아니오로 판정할 수 있게 한다. 사람 호불호는 확인하지 못한다는 한계를 쓴다.
- Build 단계 분해(1단계는 메뉴 전용 CSS·토큰·배경 레이어로 되는 것부터), 파일 소유권, 시험 영향(기준값 일반용 123 / 교육용 301(건너뜀 1) / 서버 65 — **일반용은 §26 S1 Build가 새 시험을 더해 개수가 늘 수 있음**), Review 기준, 되돌리기.
- **진행 중인 다른 계획과의 충돌·순서**: §26 S1·S2(보드, `game.js`만, 메뉴와 파일 안 겹침), §27 M1·M2(레벨 카드·결과 화면·`.stage-detail` — **레벨 선택 B와 같은 화면**), §28(점수 표기). 레벨 선택 B를 §27 M2 전/후/동시 중 언제 넣을지 권장과 근거.
- 열린 질문(번호, 권장안 먼저).
