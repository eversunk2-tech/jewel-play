## 배경 (사용자 요청, 2026-11-19)
사용자는 시작 화면의 난이도 막대(초보·중수·고수·최고점 도전 모드 칸, 선택된 "중수"는 노란 칸 아래에 연보라 받침이 붙음), 규칙 설명 줄, [시작] 버튼(아래 갈색 받침), 프로필 알약(`헌터헌터 #7648 수정` + `클리어 10/10 · 별 16`, 보라 테두리 + 아래 받침), 스테이지 카드(초록 카드 아래 두꺼운 초록 받침)의 캡처를 보여 주며 이렇게 말했다: *"메뉴바 등에서 약간 입체느낌을 살린다는 식으로 아래쪽이나 옆쪽에 덧붙는 부분이 있잖아. 이런 부분이 AI 특유의 디자인이라서 없는 게 좋다는 사람이 있는데 이점에 대해 어떻게 생각해? 이런 식으로 하지 않고 실제 사람 전문 디자이너들이 웹디자인 할 때 메뉴바를 밋밋하지 않게 표현하는 방식을 분석해서 시안을 제시해줘. 그리고 내 승인에 따라 게임 UI의 모든 메뉴바, 버튼 등에서 이러한 디자인을 수정해줘."*
→ 사용자가 원하는 것: ① 이 "받침(립)" 표현에 대한 근거 있는 의견 ② 전문 디자이너가 평면적이지 않게 표현하는 방식의 **분석** ③ **실제 게임 화면 시안**(승인용) ④ (승인 뒤) 두 앱 전체 UI에 적용. 이 지침은 ①~③과 ④를 위한 범위·위험 정리까지다.
대상 사용자는 **초등학생 이상 전체 이용가**이고 PC·태블릿 사용이 많다(**시안은 PC 가로 1280×720을 첫 장**으로, 폰 390×844는 보조). 터치 타깃 44px, 글자 대비 WCAG AA(4.5:1)는 유지해야 한다.

## 할 일

### 1. 인벤토리 (범위 파악 — 표로)
- "립"은 `box-shadow`의 `0 Npx 0 <색>`(받침)·`inset 0 -3px 0`·흰 바깥 테두리(`border: 2~3px solid #fff`)·그 위에 겹친 드롭 섀도 조합이다. `grep -nE "box-shadow:[^;]*0 [2-9]px 0|0 1[0-2]px 0"`로 `style.css` 86줄·`edu.css` 19줄을 찾았다(메인 세션 1차 집계; 정확히 다시 센다).
- 규칙을 **요소 종류별로 묶는다**: ① 주요 행동 버튼(`#btn-start`, `.btn.primary`, `#btn-chal-again` …) ② 보조 버튼(`.btn`, `.btn.ghost`, `#btn-hint/menu/reset`, `.btn.hall`, `.btn.danger`) ③ 선택 칸(`.level-select`/`.level-btn`, `.hf-tabs`/`.hf-tab`, 교육용 문제 양 라디오 `.eg-amt`) ④ 정보 줄·알약(`.level-desc`, `.best-line`, `.me-chip`, `.myrank`, `.timer`/`.scorebar`/`.goal`/`.gauge`) ⑤ 카드·행(`.stage-card` 상태별, `.hr`, `.av-btn`) ⑥ 제목·패널(`#end-title`, `#pause-title`, `#chal-end-title`, 오버레이 패널, 교육용 문제 팝업 `#eg-quiz`·단원 카드). 각 묶음의 **선택자·줄 번호·규칙 수**, **누를 수 있는 것(interactive)인지 정보(static)인지**, 주요/보조 구분을 적는다.
- **레이아웃 의존**: 립 두께가 높이·간격·`--ui-h`(HUD 합 302px)·`--board` 계산·스테이지 그리드에 섞여 있는지, 립을 없애거나 줄이면 어디가 움직이는지. `style.css`의 겹쳐 쓰기 층(원래 ~1100행·와이드 레이아웃·메뉴 V1 U-A/U-B 블록 ~1980행 이후·최고점 도전 4번째 칸 블록)을 구분하고, **마지막에 덧붙이는 "토큰 + 덮어쓰기 블록" 한 곳으로 바꾸는 방식**(U-A/U-B가 쓴 방식)이 가능한지 판단한다.
- **시험이 CSS를 핀으로 묶는 곳**: `apps/element-gems/test/*.js`·`apps/element-gems-edu/test/*.js`에서 `style.css`·`edu.css`를 읽는 시험(예: `menu.test.js`·`widescreen.test.js`·`challenge.test.js`·`erase.test.js` …)이 어떤 선택자·값을 단언하는지 목록화한다(Build 때 기대값을 고쳐야 할 곳).

### 2. 조사 (전문 디자이너는 어떻게 하나) — 출처 필수
웹 검색·문서 읽기로 **실제 근거**를 모은다(검색어·읽은 주소·확인 날짜를 적고, 읽지 못한 것은 "확인하지 못함"으로 쓴다). 사람이 쓴 글·디자인 시스템 문서 위주. 다룰 주제:
- 평면(flat)이지 않게 보이게 하는 **전문가의 수단**: 색조 층(tonal surface)·면 대비, 1px 헤어라인 테두리와 안쪽 윗 하이라이트, 겹친 부드러운 그림자(접촉 그림자 + 넓은 확산 그림자, **바닥색과 같은 색조로 물들인 그림자**), 파인 트랙 + 떠 있는 선택칩(segmented control), 반투명·블러(frosted), 선택 상태의 면·굵기 변화, 타이포·간격·아이콘으로 위계, 눌림·호버 반응(micro-interaction)으로 입체감을 "동작"으로 주기.
- **"아래 두꺼운 받침 버튼"의 출처와 용도**: 캐주얼 게임·Duolingo류의 chunky/3D 버튼이 어떤 이유(눌림 가능성 암시)로 쓰였는지, 디자이너 사이에서 어떤 비판("AI 같다", 과장·획일적 효과)이 있는지, 언제 쓰고 언제 피하는지. Material 3(elevation·tonal), Apple HIG(materials·segmented control), 게임 UI(King·Supercell·Playrix류의 프레임·베벨) 등에서 **어린이·캐주얼 대상**과 **성인·SaaS** 대상의 차이.
- "AI 티"라고 느껴지는 **구체적 징후**(획일 적용·겹겹 효과·모든 요소 같은 비중·보라 계열 그림자 등)가 글로 정리된 것이 있으면 인용(없으면 "정리된 글을 찾지 못함"). 사용자가 말한 "AI 특유"는 **증명된 사실이 아니라 일부 사람의 인상**이다 — 단정하지 말고 근거 수준을 적는다.
- 결과를 **한 쪽 표**("수단 / 효과 / 어린이 대상에서의 장단점 / 이 게임에 적용 가능한 형태")로 요약한다.

### 3. 시안 (실제 게임 화면 위에, PC 가로 우선)
**현재(cur)** + 아래 3종을 같은 화면·같은 상태로 촬영한다. 시안은 scratchpad 사본에 **덮어쓰기 CSS 파일 하나**(`ui-depth-A.css`·`-B.css`·`-C.css`)를 `style.css` 뒤에 붙이는 방식으로 만든다(= Build 때 쓸 방식의 사전 검증). 같은 토큰(`--elev-*` 등)을 정의해 규칙이 몇 개 필요한지 센다.
- **A. 정돈된 입체(절제형, 메인 세션 권장 후보)**: 게임다운 말랑함·원색 포인트는 유지하되 **위계를 만든다**. ① 정보 요소(`.level-desc`·알약·`.timer`/`.scorebar`/`.goal`/`.gauge`·카드의 정보 부분·랭킹 행)는 **받침 없음·흰 바깥 테두리 없음**: 반투명/연한 면 + 1px 헤어라인(잉크색 약 12~18%) + 윗 1px 하이라이트 + 겹친 부드러운 그림자(색조 입힘). ② 선택 칸(난이도·탭)은 **파인 트랙(안쪽 그림자) 위의 선택칩**: 선택 칸은 주색 면 + 부드러운 그림자, 받침 없음. ③ **주요 행동 버튼([시작]·[다시 도전] 등) 하나만** 얇은 받침(약 3~4px, 같은 색 계열로 더 어둡게, 흰 바깥 테두리 없음)을 남겨 "누르는 것"을 알리고, 누르면 받침만큼 내려앉는다. ④ 보조 버튼은 색조 면 + 헤어라인 + 부드러운 그림자(받침 없음), 누르면 살짝 작아짐.
- **B. 플랫·유리(현대 웹 느낌)**: 받침 **전부 없음**. 반투명 블러 패널(`backdrop-filter`)·헤어라인·부드러운 색조 그림자·선택칩은 채운 알약 + 그림자. 주요 버튼은 채운 그라데이션 + 윗 하이라이트 + 주색으로 물든 확산 그림자, 눌림은 `scale(.97)`. (블러가 저사양 폰에서 부담이 되는지 메모.)
- **C. 정리된 말랑(현재 개성 유지, 규칙만 정돈)**: 받침은 **누를 수 있는 것(주요·보조 버튼, 선택된 칸, 스테이지 카드)에만** 남기고 **정보 줄·알약·HUD·랭킹 행은 평면**으로. 받침은 **한 가지 규칙**(두께 4px·같은 색상 계열로 어둡게·흰 바깥 테두리와 겹친 드롭 섀도 제거).
- **촬영할 화면(각각 cur·A·B·C)**: ① 시작 화면(난이도 막대 중수 선택 + 설명 줄 + [시작] + 프로필 알약) ② 스테이지 선택(카드: 클리어·현재·잠김) ③ 플레이 중 HUD(타이머·점수·목표·게이지·버튼 3개) ④ 명예의 전당(탭 + 행 + 내 순위) ⑤ 교육용 시작 화면(단원 카드 + 문제 양 "보통/많이" 라디오 + 난이도 막대) 또는 문제 팝업. **PC 가로 1280×720을 모두**, 시작 화면·스테이지 선택은 폰 390×844도 보조로. 같은 화면 4종은 **한 장의 비교표(2×2, 라벨 "현재 / A 절제형 / B 플랫·유리 / C 정리된 말랑")**로도 합쳐 만든다(헤드리스 Chrome으로 HTML 비교표를 찍으면 된다).
- 촬영 도구: 이전 세션의 캡처 하니스를 복사해 쓴다 — `~/Documents/원소보석 작업 백업/2026-11-10-promo-qreview-difficulty/promo/h/`(`cdp.mjs`·`lib.mjs`·`serve.mjs`·`patch.mjs`(사본에 `apiBase`→로컬 목 서버와 `window.__eg` 훅을 심음)·`gen-shots.mjs`·`edu-final.mjs`·`profile-shot.mjs`). **그 뒤 앱이 바뀌었다**(난이도 4번째 칸·도전 모드·문제 양 기본 "보통" 등)니 그대로 돌아가지 않으면 새 화면 구조에 맞게 고쳐 쓴다. 비우면 프로필·명예의 전당 UI가 꺼지니(`apiBase`) 촬영 사본에는 로컬 목 서버를 붙인다. 화면의 점수·별·'내 순위'는 자동 플레이 화면이므로 "예시"임을 메모한다.
- 파일명은 **역할 이름**으로: `ui-depth-start-cur-1280.png`, `ui-depth-start-A-1280.png` …, 비교표 `ui-depth-compare-start-1280.png` 등.

### 4. 각 시안의 측정·평가 (표로)
각 시안(A·B·C)에 대해 **직접 측정**: ① 글자 대비(주요 조합 5~8개, 수치) ② 누를 수 있는 것의 경계/상태 식별(비텍스트 대비 3:1 또는 다른 단서) ③ 터치 타깃 44px 유지 ④ 문서 높이·보드 크기·`--ui-h` 변화(현재 대비, 레이아웃이 움직이는지) ⑤ 눌림·호버·포커스·비활성 상태 그림(작은 비교 이미지) ⑥ 저사양 부담(블러·겹친 그림자 개수) ⑦ Build 작업량(바꿔야 할 규칙 수·시험에서 바뀌는 곳·두 앱 동기화 부담)과 위험. 각 시안의 **장단점을 어린이 대상 사용성(누르는 것임이 보이는가)과 "AI 티"/위계 관점에서** 정직하게 적는다(근거 없이 단정하지 않는다).
