# Plan 지침 — 애니팡 점수 시스템 벤치마킹과 점수 규칙 개선안 (spec §28 신규)

## 역할
너는 **Plan 담당**(Sonnet 서브에이전트)이다. 구현하지 않는다. 결과는 `apps/element-gems/spec.md` **맨 끝에 `## 28.`로 한 번에 추가**한다(`cat >> spec.md <<'EOF' … EOF`, 기존 §는 **읽기만**, 수정·삭제 금지). 번호는 **§28으로 예약**되어 있다. **§26(3492~3875행, 보드 구조 사다리)과 §27(3877~4312행, 목표 유형·미션·비폭력 특별 레벨·선물상자)이 이미 들어 있다 — 둘 다 읽기만 하고 수정하지 않는다.** §27(특히 §27.3 미션 카탈로그와 민감도, 초보 점수 10레벨 표, 교육용 ×1.2→1.8 논의)을 먼저 읽고 §28이 그것과 어떻게 맞물리는지 쓴다. 파일 끝이 바뀌었는지 쓰기 직전에 `tail`로 확인한다.
프로젝트 규칙은 `CLAUDE.md`, 진행 상황은 `docs/STATUS.md` §14를 먼저 읽는다.

## 우리 현재 점수 규칙 (코드로 직접 확인할 것: `apps/element-gems/game.js` `CONFIG.score`·`baseScore`·`chainMult`·`awardGroup` 부근, 약 28~33행·395~399행·1331~1395행)
기본 점수 3매치 50 / 4매치 100 / 5매치 200 / 6개 이상 200+100×(크기−5), **연쇄 배율 = 연쇄 단계(1~5, 상한 `chainMax`=5)**, 어둠 스킬 ×2(8초), 스킬 칸당 `skillCell`=10점(연쇄 1 고정), 난이도 점수 배율 ×0.8/1.0/1.3(초보/중수/고수), 시간 보너스(3/4/5+매치, 연쇄 2단계 이상 `chainExtra`)는 점수와 별도. 현재 목표 점수는 `CONFIG.stages.targets`(§25.6: 초보 3500…6100, 중수 4500…8200, 고수 5500…9900, 교육용 ×1.2). 교육용은 정답 보너스(240/300/390)가 목표 점수에 더해진다.

## 이미 정해진 것 (충돌하면 이 항목이 우선)
1. **방향 E(사용자 선택)**: 초보만 점수 목표, 중수·고수는 레벨별 미션(§27, 계획 중). → 점수 규칙을 바꿔도 **직접 영향을 받는 것은 초보의 목표 점수·모든 난이도의 결과 점수·별(남은 시간)**이다. 이 연관을 계획서에 분명히 쓴다.
2. 초보 1단계 목표는 **4000에서 시작**하는 것이 사용자 요청이다(일반용/교육용 화면값 해석은 §27의 열린 질문). 점수 규칙을 바꾸면 이 숫자의 의미가 바뀌므로, **규칙을 바꾸는 안은 "목표를 같이 다시 맞추는 방법"을 반드시 포함**한다.
3. **별은 남은 시간 기준**이고 서버(`server/src/core.js`)는 스테이지 10개·최대 별 점수 180·별 기준 30/50%를 고정해 쓴다. **서버 변경이 필요한 안은 "서버 변경 필요"로 크게 표시**하고 기본 권장에서 제외한다(Worker 재배포는 사용자가 직접 해야 하고 새 승인이 필요). 목표 점수는 서버가 보지 않으므로 바꿔도 서버 변경이 없다. 점수 랭킹형 모드(순위 서버)는 **장기 후보로만** 설명하고 상세 설계하지 않는다.
4. **전체 이용가**(도박·과금·외부 링크 유도 금지, 비폭력). 피버·콤보 연출은 가능하나 도박 느낌의 무작위 보상은 넣지 않는다. 두 버전(일반용·교육용) **동일 규칙**, 교육용 ×1.2·정답 보너스와의 상호작용을 계산한다. 교육용 선물상자는 한 화면 동시 최대 6개(사용자 결정, §27이 다룸).
5. §26(보드 구조 사다리, 이미 spec에 있음, 승인 전)은 연쇄 빈도에 영향을 줄 수 있다. §28은 **현재 균등 무작위 보드를 기준선**으로 평가하고, §26과 독립적으로 적용 가능한지(직교성) 한 문단으로 적는다.

## 해야 할 일
1. **보강 조사(웹)**: 애니팡 1편의 점수·콤보·피버·특수 블록·라스트팡 규칙을 가능한 한 더 찾는다(공략 글·위키·커뮤니티). 수치마다 **출처와 확신 수준**(공식/위키 검증요망/추정)을 표로 쓴다. 비슷한 한정 시간 점수 경쟁 게임(비쥬얼드 라이트닝, 팝캡 계열 등)의 점수 구조도 **확인된 것만** 간단히 비교한다. 못 찾은 것은 못 찾았다고 쓴다.
2. **우리 점수 구조 해부**: 판당 점수의 출처 비율(기본 매치 / 연쇄 2단계 이상 / 스킬 / 어둠 배율)을 실제 `game.js` 규칙으로 측정한다(§26 보고에 "중수 규칙에서 점수의 약 59%가 2단계 이상 연쇄에서 나온다"는 수치가 있다 — 재측정해 일치 여부 확인). 플레이어 유형별 **점수 분포 폭**(예: 빠른·스킬 씀 대 느린·스킬 안 씀의 점수비, 표준편차/평균)도 잰다.
3. **개선 후보 설계와 평가** — 최소한 다음을 비교한다(필요하면 더 제안, 단 모두 `CONFIG` 한 곳에서 조정 가능하게):
   - **A. 현상 유지**(대조군) + 숫자 단위만 키우기(표시 배율): 체감은 바뀌고 어려움은 그대로임을 확인.
   - **B. 연쇄 상한 완화**: `chainMax` 5 → 7·10·상한 없음, 또는 완만한 증가 곡선. 시간 보너스·어둠 배율과의 곱 폭주 위험(최대 점수)을 계산.
   - **C. 행동 사이로 이어지는 콤보(애니팡식)**: 일정 시간(예: 2초) 안에 다음 매치를 하면 콤보 단계 유지 → 배율. 타임아웃 값 후보와 "생각 오래 하면 끊김"이 초보에게 주는 부담(초보는 유지 시간 길게 등).
   - **D. 피버식 보상**: 콤보 N단계마다 짧은 피버(점수 배율 또는 매치 시 주변 보석 추가 제거). **스킬(불·풀)과 겹치는지·원소 스킬 컨셉과 어울리는지** 판단.
   - **E. 스킬 점수 확대**: `skillCell` 인상, 스킬 사용 1회당 일시불 점수, 종료 시 남은 게이지 정산(라스트팡 식, 단 **도박·강제 사용 느낌 없이**). 스킬을 안 쓰는 플레이어가 중수 이후 막히는 문제(R3 §22)에 주는 영향.
   - **F. 점수 도전(하이스코어) 보기**: 미션 레벨(§27)에서 점수는 목표가 아니라 **기록**(레벨별 최고 점수, 별 외 보조 표시)으로만 보여 애니팡 같은 "더 높이" 동기를 주는 안, 또는 **로컬 기록만 쓰는 '점수 도전' 모드**(서버 없음, `localStorage`). 서버 순위가 필요한 부분은 "서버 변경 필요"로 분리.
   - 조합안(예: C+D, B+E)도 평가한다.
4. **시뮬레이션(필수)**: 실제 `game.js` 규칙 함수를 `require`해(읽기 전용) 수당 생각시간×스킬 사용×수 고르기 기준 플레이어 9종(§25 머리말 모델: 수당 2.0·3.0·4.0초 × 스킬 0/30/60% × 무작위/최선3), 셀당 **600판 이상**(권장 2,000), 시드·조건 명시. 재사용 가능한 읽기 전용 참고: `/private/tmp/claude-501/-Users-sungchul-Desktop-play2-jewel-play/a531f417-6e12-4899-8faf-38c202023dbb/scratchpad/diff/sim-human.js`, §26 에이전트의 `.../scratchpad/plan-board/`. 작업 파일은 `.../scratchpad/plan-score/`에만 둔다. 후보마다 다음을 표로 쓴다: ① 점수 분포 폭(상위/하위 플레이어 점수비) ② §25.6 목표 대비 클리어율 변화와 **목표를 같은 클리어율로 다시 맞춘 값**(초보 10단계 표, 100점 반올림, 교육용 ×1.2 참고) ③ 별(3★/2★ 비율) 변화 ④ 최대/상위 1% 판 점수(폭주 여부) ⑤ 판당 평균 연쇄·콤보 길이 ⑥ 교육용(? 최대 2개와 6개 두 경우, 정답률 75% 가정, 정답 보너스 포함) 영향.
   모델 한계(불·풀 조준 무작위, 자동 힌트 미반영, 일정한 속도)와 **사람 체감은 확인하지 못했다**는 점을 항상 쓴다.
5. **권장안 하나**를 근거와 함께 정한다(비교·판단 요청이므로 한쪽을 권한다). "하지 않는 것이 낫다"도 가능한 권장이다 — 단, 이유를 수치로. 사용자의 "점수의 벽" 느낌이 **규칙 때문인지 목표 점수 구조 때문인지**를 분리해 설명한다(방향 E가 중수·고수를 이미 해결하는 범위와 §28이 추가로 해결하는 범위).
6. **영향 범위·위험**: 두 앱 동기화 범위(`game.js` `CONFIG.score`, 시험 기대값 등), 서버 영향(없음 확인), 저장 데이터 호환(기존 최고 점수·진행 기록이 의미가 바뀌는 문제와 처리 방법), §26·§27과의 순서, 기존 시험 기준값(일반용 123 / 교육용 301(건너뜀 1) / 서버 65)에 미치는 영향, Build·Review 단계 분해(파일 소유권 포함).
7. **열린 질문**을 번호로, 각 질문에 권장안을 먼저 적는다.
