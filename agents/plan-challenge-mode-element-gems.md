### A. 게임 설계 (사용자에게 승인받을 설계. 열린 질문마다 **권장안을 먼저, 이유 한 줄**)
1. **규칙**: 2분(120초) 점수 도전. 질문: ① 시간 보너스(3·4·5개 매치 시 시간 증가)를 켤지(켜면 2분보다 길어짐) — 사용자가 "2분 동안"이라고 했으므로 **고정 120초 권장**, 근거를 점수 분포로 ② 어떤 난이도 프리셋(보드 구조·게이지 크기·스킬 효과·힌트·콤보창·점수 배율)을 쓰는가 — 중수 기반 vs 고수 기반 vs 새 프리셋(공정한 단일 순위를 위해 **하나로 고정** 권장), 근거 ③ 점수 규칙은 §28 그대로(콤보·스킬 점수 ×3 규모)인가 ④ 목표 점수·레벨·별 없음, 종료는 시간 0 ⑤ 일시정지·재도전 ⑥ 기록 대상(개인 최고 점수만? 최근 기록·플레이 횟수도?).
2. **들어가는 곳·해금**: 시작 화면 어디에 어떻게 둘지, **해금 조건**(30단계 모두 클리어 후 / 한 난이도 10단계 클리어 후 / 처음부터 열림)을 선택지와 권장으로. 사용자의 동기("모든 단계를 클리어한 뒤 도전할 것이 없다")를 기준으로 하되 좌절 요소가 없게 판단.
3. **화면**: 시작 화면 진입, 도전 중 HUD(점수·남은 시간), 결과 화면(점수·내 최고·신기록 표시·다시 하기·돌아가기), 명예의 전당에서 최고점의 표시 여부. 모바일(터치 타깃 44px·세로/가로)·색약 접근성·`prefers-reduced-motion` 고려. 초등학생이 읽는 쉬운 말 문구 초안. **화면 시안**을 정적 HTML 하나(`mock.html`, 외부 의존 없음)와 설명으로 만든다.
4. **저장**: 로컬 저장 구조 변경(기존 키 `element-gems:v1` 호환·마이그레이션; 기존 저장은 깨지지 않아야 한다), "프로필 지우기는 이 기기에서만 지운다" 규칙과의 관계.

### B. 서버·D1 설계 (코드는 짜지 않는다. 변경 목록과 SQL 초안)
1. **스키마**: `best_score INTEGER NOT NULL DEFAULT 0` 추가용 마이그레이션 SQL(사용자가 **D1 콘솔에 붙여 넣는** 한 문장 + 확인 쿼리), 새 설치용 `schema.sql` 수정안, 필요하면 `up_score`(동점 선착순용 시각) 같은 보조 열 필요성 판단. **ALTER TABLE ADD COLUMN이 D1(SQLite)에서 가능한 제약**(NOT NULL은 DEFAULT 필요 등)을 확인하고, 로컬 SQLite(`node:sqlite`, Node 24)로 마이그레이션 → 새 쿼리 → 순위 결과를 가짜 데이터 시험으로 확인한다(D1에서 직접 못 해 본 부분은 한계에 적는다).
2. **정렬·순위**: 새 정렬 키는 `별 개수 → 최고점 → 남은 시간(left) → 먼저 달성(up) → id`. 질문: 이 규칙을 **전체·초보·중수·고수 네 탭 모두**에 쓸지(사용자는 "별 개수 같을 때는 최고 기록 점수로"라고만 말함) — 권장과 이유. `boardTop`·`rank`(내 순위 계산식)·부분 인덱스 4개(`idx_rank_*`) 재정의 SQL(DROP/CREATE), `EXPLAIN QUERY PLAN`으로 인덱스가 정렬에 쓰이는지 로컬 SQLite에서 확인.
3. **API**: `POST /api/sync`에 선택 필드(예: `s` = 최고점 정수)를 추가하는 안. **옛 클라이언트와 호환**(필드 없으면 변화 없음), `API_VERSION` 유지/올림 판단, `validateProgress`처럼 형식 검증(정수·범위), 점수는 감소 불가(최댓값 병합), 쓰기 간격(3초)·"개선 시에만 쓰기" 유지, 응답 `me`·순위표 행에 최고점 노출 여부(권장).
4. **점수 상한(anti-cheat)**: 서버는 점수를 재현·검증하지 못한다(§19 위험 허용 수준 참조). 상한을 **시뮬레이션 근거**로 정한다: Plan 하네스(`/private/tmp/claude-501/-Users-sungchul-Desktop-play2-jewel-play/a531f417-6e12-4899-8faf-38c202023dbb/scratchpad/plan-mission-raise2/work/` 의 `h.js`·`bot.js`·`sim.js`·`pool.js`·`lib.js`, 읽기 전용으로 새 폴더에 복사해서 쓴다)로 A.1에서 정한 규칙(고정 120초, 선택한 프리셋)의 점수를 B·A·X1·X2·X3(1.0초·스킬 90%·조준 95%) 등 플레이어별 **300판 이상** 돌려 분포(평균·p50·p95·최대)를 구하고, 상한 = 관측 최댓값에 안전계수를 곱한 값 + 이유. 이상치 점검 SQL(상한 근처 점수 사람 찾기)과 관리자 숨김 절차(§19.4.6) 연결. 점수 모드 해금을 서버가 검사할지(예: 30단계 모두 클리어한 진행 기록이 있어야 점수 접수)도 판단한다.
5. **무료 한도 재계산**: §19.4.7 표를 이 변경 반영해 다시 쓴다(새 열이 4개 부분 인덱스에 들어가므로 최고점 개선 1회 = 표 1행 + 인덱스 갱신 행; "D1 쓴 행에 인덱스 갱신 포함" 보수적 가정 유지). 시나리오: 500명·1,000명, 사람당 하루 최고점 개선 5·10·20회. 클라이언트의 **제출 묶기**(게임 끝날 때가 아니라 개선된 최고점만, 일정 간격/화면 나갈 때)로 쓰기를 줄이는 안. 읽기 한도(내 순위 스캔)와의 관계, 한도 초과 시 동작.
6. **배포·마이그레이션 절차(사용자 직접 할 일)**: 순서 **① D1 콘솔에서 ALTER(+인덱스 재생성) ② Worker `dist/worker.js` 배포 ③ 사이트 푸시**, 각 단계의 정확한 클릭 위치·붙여넣을 SQL·확인 쿼리, 순서를 어겼을 때 일어나는 일, 되돌리기(롤백) 방법. 사용자는 이전에 대시보드 Worker "Edit code" 붙여넣기와 D1 Console SQL 실행을 해 본 적이 있다.

## 규칙·제약 (지킬 것)
- 서버는 **명예의 전당(닉네임·아바타·별 순위) 예외** 안에서만 쓴다. 새 열은 정수 점수 하나이며 이 요청의 범위다(§19 예외 범위를 "넘는지"를 한 줄로 판단해 적고 사용자 승인 항목으로 표시).
- 서버가 없거나 실패해도 **게임은 완전히 동작**(오프라인 폴백). 점수 모드도 서버 없이 로컬 최고점으로 동작해야 한다.
- 모든 수치는 `CONFIG` 한 곳. 비밀키·토큰·계정 정보를 다루지 않는다(`wrangler login/deploy/secret` 실행 금지, 사용자가 직접 한다).
- 시뮬레이션 규칙: 플레이어와 한계를 적는다(조준·스킬은 가정값, 사람 체감은 확인하지 못함). 시드 **91,000,000~** 이상을 쓰고(다른 작업이 81~83백만대 사용), 워커 **최대 3개**, 힙 1.5GB, 10작업마다 워커 재시작, 긴 작업은 백그라운드로(포그라운드 `sleep` 금지).
- 확인하지 못한 것(청각·실기기·D1에서 직접 실행·사람 체감)은 "확인함"으로 쓰지 않는다.
